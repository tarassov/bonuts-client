# План оптимизации Cypress-тестов

Статус: черновик · Автор: обсуждение с Claude · Дата: 2026-07-19

Цель — устранить системные слабости текущей архитектуры e2e-тестов и закрыть
главный риск полностью замоканного набора (расхождение контракта фронт↔бэк),
не жертвуя скоростью и детерминизмом CI.

## Текущее состояние

```
cypress/
├── e2e/                    login, dashboard-card, give-modal, profile-page, vk-callback, welcome-invitation
├── support/
│   ├── commands.ts         visitAuthorized / mockAuthorization (авторизация через localStorage)
│   ├── dashboard-page.ts   моки дашборда + visitDashboard (page-object)
│   ├── vk-callback.ts       моки VK-флоу
│   ├── viewports.ts         runInViewports (desktop/mobile)
│   └── fixtures/profile-response.ts
└── cypress.config.ts       baseUrl https://localhost:3002
```

Базовая архитектура здоровая: есть кастомные команды, page-object-хелперы,
вынесенные фикстуры, обёртка для адаптивности. Ниже — что улучшить.

---

## Часть 1. Рефакторинг и чистка (быстрые победы)

### 1.1 Убрать дублирование `visitDashboard`
- **Проблема:** функция объявлена в `support/dashboard-page.ts:213` и заново
  продублирована локально в `e2e/dashboard-card.cy.ts:7`.
- **Действие:** удалить локальную копию, импортировать из `support/dashboard-page.ts`.

### 1.2 Убрать условные assert'ы (антипаттерн «молчаливый skip»)
- **Проблема:** `assertNotificationCardPresentation` в `dashboard-card.cy.ts:19`
  содержит «если карточки нет — залогировать, `cy.reload()` и выйти». Данные
  замоканы → карточка обязана присутствовать всегда. Условный выход скрывает
  реальные падения и создаёт ложную зелень.
- **Действие:** заменить на детерминированное ожидание (`should("be.visible")`)
  без ветки «а вдруг её нет». Мок гарантирует наличие карточки.

### 1.3 Унифицировать перехват запросов
- **Проблема:** часть моков через glob (`"**/profile*"`), часть через
  regex-константы (`/\/profile(?:\?.*)?$/`) с проверкой `request.query.tenant`.
- **Действие:** привести все моки к regex + проверка tenant (более надёжный
  вариант, уже используется в `profile-page.cy.ts` и `vk-callback.ts`).

### 1.4 Дописать реальный сценарий в `give-modal.cy.ts`
- **Проблема:** спек проверяет только видимость кнопки (`give-modal.cy.ts:13`),
  хотя `mockGiveDonutsModalRequests` в `dashboard-page.ts:188` уже готовит
  `transfer`-эндпоинт и весь мок-контур.
- **Действие:** дописать e2e-сценарий «открыть модалку → выбрать коллегу →
  выдать донат → проверить `@postTransferDonuts`». Либо убрать мёртвый мок.

### 1.5 Снять хрупкую привязку к внутренним классам MUI
- **Проблема:** `.MuiCardHeader-avatar`, `.MuiChip-root`, `.MuiAutocomplete-root`,
  проверка `padding-top: 10px` — ломается при апдейте MUI/смене стилей.
- **Действие:** где возможно — перевести на `data-testid`. Проверки конкретных
  CSS-значений оставлять только там, где именно верстка является предметом теста.

### 1.6 Вынести boilerplate-моки в глобальный beforeEach
- **Проблема:** `heartbeat`, `profile`, `tenants` мокаются почти в каждом спеке.
- **Действие:** дефолтные заглушки нейтральных эндпоинтов — в `support/e2e.ts`
  (глобальный `beforeEach`). Спеки переопределяют только значимое.

### 1.7 Единый файл селекторов
- **Проблема:** `data-testid`-строки размазаны по спекам.
- **Действие:** `support/selectors.ts` с константами — снижает хрупкость и
  упрощает переименования.

## Часть 2. Контракт с бэкендом (главный риск)

Полностью замоканный набор не ловит расхождение контракта фронт↔бэк: бэкенд
поменял поле — тесты зелёные, потому что рукописный мок остался старым. Ложная
уверенность.

У проекта **уже есть OpenAPI**: `openapi-config.ts` генерирует типы из swagger
(`http://127.0.0.1:3003/api-docs/v1/swagger.json`) в `src/services/api/bonuts-api.ts`.
Это даёт дешёвое решение без перехода на реальный API.

### 2.1 Типизировать фикстуры генерёнными из OpenAPI типами
- **Действие:** аннотировать моки типами из сгенерированного API-слоя, напр.
  `PROFILE_RESPONSE: components["schemas"]["Profile"]`.
- **Эффект:** при пересборке типов из swagger протухший мок падает на `tsc`,
  а не проходит молча. ~80% ценности «реального API» почти бесплатно.

### 2.2 (Опционально) Валидация фикстур против схемы
- Проверять, что мок-объекты соответствуют OpenAPI-схеме (schema validation).
  Дороже пункта 2.1, брать при необходимости.

## Часть 3. Smoke-набор на реальном API

**Мокать по умолчанию — правильно.** Основную массу тестов держим на моках.
Дополнительно — маленький точечный набор против **живого staging-бэкенда**,
чтобы поймать интеграцию, которую моки принципиально не видят.

### 3.1 Отличия от текущих тестов

| | Текущие (моки) | Smoke (реальный API) |
|---|---|---|
| Данные | `cy.intercept` + фикстуры | живой staging-бэкенд |
| Что ловит | UI, рендер, логику фронта | контракт фронт↔бэк, интеграцию |
| Скорость/стабильность | быстро, детерминированно | медленно, возможны флейки |
| Когда гонять | каждый PR, блокирует merge | nightly / перед релизом, **не** блокирует PR |
| Объём | много (вся UI-логика) | 2–3 критичных флоу (логин→дашборд, выдать донат) |

### 3.2 Тестовый пользователь и креды

Реальный пользователь создаётся, но **не «один на всех, пароль в гите»**.
Выбранный подход — вариант 1 + принципы изоляции:

- **Seed-юзер** на staging: `e2e@bonuts.test` в **отдельном тестовом tenant**.
- Креды **не в репозитории**:
  - CI: GitHub Actions Secrets → env → `Cypress.env("E2E_PASSWORD")`.
  - Локально: `cypress.env.json` в `.gitignore`; в репо только
    `cypress.env.json.example` с пустыми полями.
- **Снизить ценность утечки** (важнее, чем прятать пароль):
  - аккаунт живёт только на staging, на проде его нет;
  - изолированный tenant — не видит данных реальных клиентов;
  - минимальные права (не админ, если сценарий не требует);
  - staging за VPN/basic-auth.
- **Продвинутый вариант (позже):** seed-эндпоинт бэкенда создаёт/удаляет
  юзера с рандомным паролем в `before`/`after` — долгоживущих кред нет вообще.

### 3.3 Реальная авторизация через `cy.session`

Логин один раз за прогон, через API, не через UI:

```ts
Cypress.Commands.add("loginReal", () => {
  cy.session("e2e-user", () => {
    cy.request("POST", "/authenticate", {
      email: Cypress.env("E2E_EMAIL"),
      password: Cypress.env("E2E_PASSWORD"),
    }).then(({ body }) => {
      window.localStorage.setItem("settings", JSON.stringify({
        auth_token: body.auth_token,
        tenant: body.currentTenant,
        locale: "en",
      }));
    });
  });
});
```

### 3.4 Изоляция набора и окружения
- Отдельная папка `cypress/smoke/` или тег + свой `specPattern`.
- `baseUrl` на staging — через отдельный конфиг / `--config baseUrl=...` / env.
- Отдельный npm-скрипт `cypress:run:smoke`.
- Отдельный CI job по расписанию (nightly), не блокирующий PR.
- Сценарии, меняющие состояние (выдать донат) — откатывать или изолировать в
  тестовом аккаунте, чтобы не засорять staging.

### 3.5 Требует согласования с бэкенд-командой
- Тестовый tenant + seed-юзер на staging.
- Наличие данных для дашборда в этом tenant (иначе реальный API вернёт пусто и
  smoke будет нечего проверять) — либо тесты терпимы к динамике («есть хотя бы
  одна карточка», а не конкретный «Bruce Wayne»).

## Порядок выполнения (рекомендуемый)

1. **Часть 1** — рефакторинг и чистка (не требует внешних зависимостей).
2. **Часть 2.1** — типизация фикстур из OpenAPI (максимум пользы за минимум сил).
3. **Часть 3** — smoke-набор (после согласования staging-окружения с бэкендом).

Части 1 и 2 можно делать сразу и независимо. Часть 3 блокируется наличием
тестового tenant/юзера на staging.
